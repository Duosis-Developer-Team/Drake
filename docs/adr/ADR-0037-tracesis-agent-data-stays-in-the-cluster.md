# ADR-0037 — Tracesis Agent: one install, the data stays in the customer's cluster

Status: accepted (2026-11-23)
Builds on: ADR-0005 (read-only cluster agent), ADR-0016 (enrollment and the
mTLS trust boundary), ADR-0026 (the production agent listener), ADR-0029
(OpenTelemetry logs and traces).

## Context

Everything Tracesis needs to observe a cluster already exists, but as three
separate installs, each tuned to one cluster:

| Piece | Today | Why it does not travel |
|---|---|---|
| Cluster agent (inventory, mTLS enrollment) | `deploy/agent` | Talks to a ClusterIP listener; nothing outside the cluster can reach it |
| OpenTelemetry agent, gateway, ClickHouse, OBI | `deploy/otel` | Namespace allowlist, node pins and Datadog opt-out written for duosis-prod-1 |
| Prometheus | `deploy/monitoring` | The API reaches it on a pinned ClusterIP |

The API reads both stores by dialling them: ClickHouse on `10.233.5.89:8123`,
Prometheus on `10.233.0.42`. That works because Tracesis and the cluster it
watches are the same cluster. It cannot work for anyone else's cluster: no
customer opens an inbound port into their cluster for a vendor.

The products people compare us with (Datadog, New Relic, Dynatrace) solve the
install half with one agent and one command, and the connectivity half by
shipping all data to the vendor. Shipping the data is exactly the cost we do
not want: ingest bandwidth, storage and retention would be ours to pay for,
for every customer, forever.

## Decision

### 1. One chart, one command: `tracesis-agent`

`deploy/tracesis-agent` is the only thing a customer installs. It is
published as an OCI chart next to the images, and the Clusters page prints
the command:

```bash
helm install tracesis-agent oci://ghcr.io/duosis-developer-team/charts/tracesis-agent \
  --version <v> -n tracesis --create-namespace -f tracesis-agent.yaml
```

`tracesis-agent.yaml` is generated by Tracesis for that cluster. It carries
the cluster's id and name, the two listener URLs, the listener CA (public
material) and a one-time enrollment token (ADR-0016: 10 minutes, single use,
stored as a hash). Nothing in it outlives the first enrollment.

The chart composes what we already run, with product defaults instead of
duosis-prod-1 pins:

- **cluster agent** (Deployment, one replica): read-only inventory as before,
  plus the query relay (§3).
- **collector agent** (DaemonSet): container logs, `k8sattributes`,
  checkpointed offsets. Every namespace except the system ones and Tracesis's
  own, unless the values narrow it.
- **collector gateway** (Deployment) and **ClickHouse** (StatefulSet) in the
  customer's cluster, same schema, TTLs and disk guard as ADR-0029.
- **Prometheus** with kube-state-metrics, node-exporter and our `drake:`
  recording rules (the community chart, as a dependency).
- **OBI** (eBPF traces): off unless `ebpf.enabled`, still an allowlist.

### 2. The data stays in the customer's cluster

Logs, traces and metrics are written to stores inside the customer's cluster
and stay there. Tracesis keeps only what it already keeps for every cluster:
catalog, inventory snapshots, heartbeats, alert state and the small rollups
the alert runner stores. Our cost per customer is that metadata, not their
telemetry.

This is also the sales argument: the customer's data never leaves their
infrastructure (KVKK, banking and public-sector buyers ask for this first).

### 3. Reads travel over the agent's own outbound connection

Tracesis never dials into the customer's cluster. The cluster agent holds a
long poll on the ingest listener (`POST /internal/v1/agent/relay/next`,
mutual TLS and the per-request proof of possession of ADR-0016). Tracesis
puts a read on that cluster's queue; the agent runs it against the
in-cluster store and posts the answer (`/relay/result`).

What the agent will run is closed and small:

| Kind | Target | Allowed |
|---|---|---|
| `clickhouse.query` | in-cluster ClickHouse, the read-only `tracesis_reader` user | the statement plus typed `param_*` values; settings only `max_result_rows`, `result_overflow_mode`, `max_execution_time`, `default_format=JSON` |
| `prometheus.query_range` | in-cluster Prometheus | `POST /api/v1/query_range` with `query`, `start`, `end`, `step` |

Anything else is refused by the agent, not just ignored. The reader's
read-only ClickHouse profile enforces the ceilings again on the server side
(1000 rows, 10 s, 512 MiB). The agent caps response bodies (4 MiB and 2 MiB,
the same caps the API applies today) and never follows a redirect.

**How this squares with ADR-0005.** ADR-0005 says commands are never pushed
to the agent and nothing dials it. Both still hold: the agent pulls work over
a connection it opened, and every request is a read of an
observability store inside the cluster. A relayed read cannot reach the
Kubernetes API, a Secret, `exec` or any write verb, because the relay has no
code path to them. A compromised control plane could read the customer's
logs and traces through it. That is the data the control plane exists to
show, so this boundary is honest about what it gives up.

**Where the switch lives.** Each cluster row carries
`telemetry_location`: `central` (the store Tracesis itself reads, as today)
or `cluster` (the cluster's own stores, through its agent). The ClickHouse
adapter routes on the scope it is already given: every scoped statement
names its cluster (`{cluster:String}`) or clusters
(`{clusters:Array(String)}`), so callers do not change. A read over several
clusters is sent to each store that holds one of them and the rows are
concatenated; every multi-cluster statement already keys its rows by
cluster, so concatenation is the correct union. Statements with no cluster
scope (development agents, AI agents) read the central store, which every
Tracesis deployment still has. Prometheus integrations name a relayed
cluster as `config_ref: agent:<cluster_ref>`; the adapter sends those reads
over the relay and every other reference through the existing SSRF-checked
connector.

**The queue is Redis.** API and worker push `{id, kind, deadline, request}`
onto `tracesis:relay:q:{cluster_id}` and block on
`tracesis:relay:r:{id}`; the listener pops for the authenticated agent's
cluster only and accepts a result only for a request issued to that cluster
(`tracesis:relay:m:{id}`). Requests past their deadline are dropped by the
listener, unanswered. An agent with no heartbeat in the last 90 seconds
fails a read at once (`store_agent_offline`) instead of waiting out the
timeout.

### 4. The listener is reachable from outside

A customer's agent must reach the enrollment (8144) and ingest (8143)
listeners. `agentListener.external` exposes both on NodePorts of the edge
host, with the listener certificate carrying that host name. The
NetworkPolicy opens those two ports to any source when exposure is on:
ADR-0026 already says the network boundary does not authenticate; the
client certificate and the proof of possession do, and they are unchanged.

### 5. Our own collector distribution

`apps/tracesis-collector` builds `tracesis-collector` with the
OpenTelemetry Collector Builder (`ocb`) from exactly the components our
configurations use, pinned to the contrib version we run (0.162.0). A
smaller binary is a smaller attack surface and a smaller image to pull, and
it is the image the chart uses. The upstream `otelcol-contrib` image stays
a supported override.

### 6. Licences and names

Everything we package is Apache 2.0: the Collector and its contrib
components, OBI, Prometheus, kube-state-metrics, node-exporter and
ClickHouse. We redistribute them under their licences, ship their `LICENSE`
and `NOTICE` files inside our images, and say "built on OpenTelemetry". We
do not use the OpenTelemetry or Prometheus names or logos as our product's
name. No AGPL component (Grafana, Loki, Tempo, Mimir) is packaged. OBI's
eBPF programs are dual-licensed GPL/BSD as the kernel requires; their
source is upstream and public.

## What this does not do yet

- **Moving duosis-prod-1 onto the chart.** Our own cluster keeps its three
  releases and `telemetry_location = central` until a planned migration that
  carries the ClickHouse volume across. Nothing in this ADR changes how it
  is read.
- **Remote configuration (OpAMP)** and a fleet page with agent versions.
  The `opamp` extension is in the distribution so this needs no new image.
- **Installing through the customer's GitOps repository.** The generated
  values file is what such a pull request would carry; the GitHub App
  would need write access to open it, which is a separate decision.
- **Published (public) images and chart.** The packages are private today.
  Customers outside the organisation need them public, or a pull secret;
  making them public is a release decision, not a code change.

## Alternatives considered

- **Ship all telemetry to Tracesis (the Datadog model).** Simplest
  connectivity, but the storage and bandwidth bill grows with every
  customer, and "your data stays with you" is lost. Rejected on cost.
- **Inbound access to the customer's stores** (VPN, NodePort, public
  ClickHouse). Every customer firewall says no, and a public store is a
  liability we would be asking them to carry. Rejected.
- **Typed query shapes instead of relayed statements.** The relay could
  carry "logs of workload X between t1 and t2" rather than SQL. It would
  move every SQL builder into the agent and freeze them at the agent's
  release cadence. The read-only reader with server-side ceilings gives the
  same safety for a read. Rejected for now; revisit if the relay ever
  needs to serve something other than Tracesis's own control plane.
- **A WebSocket or gRPC stream from the agent.** Lower latency than a long
  poll, but it needs a second listener protocol through the same mTLS and
  proof-of-possession checks. The long poll reuses both unchanged.
